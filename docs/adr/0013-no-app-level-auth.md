# 0013. アプリケーション層の認証・認可は導入しない

## Context

GitHub OAuthなどでログインを必須にする(認証)ことに加えて、ユーザーごとに
「メトリクス・ログの閲覧のみ」「チャットで調査もできる」「再起動・スケールなどの
破壊的操作まで行える」のようにロールで操作範囲を分ける(認可)ことも検討した。
運用ツールである以上、誰でも触れる状態にしておくのは望ましくなく、再起動・スケール
のような破壊的操作まで行えることを踏まえるとなおさら、というのが動機だった。

## Decision

どちらも現時点では導入しない。`infra/vpc.tf`のセキュリティグループがSSH/Web
(80/8000番)を`my_ip`(`infra/variable.tf`の`my_ip`変数)のみに許可しており、
アクセスできるのはすでにこの1人だけになっている。1人しかアクセスできない以上、
その1人にロールを割り当てる意味もない。認証・認可をアプリ層に足しても、できることの
範囲は変わらないため、機能的な意味がない。

## Consequences

- セキュリティグループの`my_ip`制限が、今のところ唯一かつ十分なアクセス制御手段になる
- 将来`my_ip`制限を外して複数人がアクセスできるようにする場合は、状況が変わる。その
  タイミングで認証・認可をセットで検討する。認可については、「読み取り専用」
  「チャット可(read-onlyツールの実行含む)」「破壊的操作可
  (`restart_service`/`scale_service`の実行含む、[ADR-0002](0002-human-in-the-loop-confirmation.md))」
  のようなロール分けが軸になる。実装するなら、`chat/engine.py`の`MUTATING_TOOLS`
  ゲート(「実行前に人間の確認を要求する」)に加えて、「そのユーザーがそもそも
  そのツールを呼べるか」を判定する層が別途必要になる
